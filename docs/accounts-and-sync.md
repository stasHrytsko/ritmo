# Аккаунты и синхронизация

Статус: решение по направлению, ничего не реализовано.
Связано с `docs/monetization.md` (подписку нельзя привязать к
анонимной локальной базе) и с отложенным разговором про напоминания
(локальное планирование для веба не существует — см. там же) —
обе темы упираются в одну и ту же недостающую часть: у Ritmo сейчас
нет бэкенда вообще.

## Два разных вопроса под одним словом «юзеры»

- **«Чтобы другой человек тоже мог пользоваться»** — уже работает
  сегодня, без единой строчки кода. Приложение целиком живёт в браузере
  устройства (IndexedDB); каждый, кто открывает ссылку, получает свою
  собственную, никак не связанную с чужой, локальную базу.
- **«Чтобы у человека была учётка, которая следует за ним между
  устройствами»** — это другое, требует настоящего бэкенда. Именно об
  этом документ ниже.

## Почему это не третья отдельная задача

Аккаунты — фундамент, на котором уже стоят две ранее обсуждённые вещи:
- Подписку (`docs/monetization.md`) невозможно продать анонимной
  локальной базе — нужно, чтобы «эта подписка» была привязана к
  конкретному человеку и была видна на его втором устройстве.
- Настоящие пуш-напоминания по расписанию тоже требуют сервера
  (локального планирования уведомлений для веба не существует, см.
  обсуждение в чате) — тот же самый недостающий кусок инфраструктуры.

## Архитектурная опора, которая уже есть

Вся бизнес-логика (`RitmoService`) обращается к данным не напрямую
через Dexie, а через интерфейс `Repositories` (routines/goals/notes и
так далее, `src/repositories/interfaces.ts`). Значит можно добавить
второй, облачный реализующий этот же интерфейс класс, не трогая ни
один экран и ни одно доменное правило — ради такого момента этот слой
и делался.

## Решения по направлению

**Авторизация — без паролей.** Email + magic link как основной способ
(пришла ссылка на почту, тапнул — вошёл). Позже можно добавить Sign in
with Apple/Google. Пароли — лишняя точка трения и лишняя
ответственность (хранить, хешировать, сбрасывать), не нужны для
личного трекера.

**Бэкенд — Supabase.** Postgres + готовая авторизация + Row Level
Security — человек физически не может увидеть чужие данные на уровне
базы, не только на уровне кода приложения.

**Локальная база остаётся основной.** IndexedDB не заменяется
«обязательно онлайн» — вся мгновенная реакция интерфейса (анимации,
отклик на тап), в которую было вложено много внимания при редизайне,
никуда не девается. Облако — второе хранилище позади того же
интерфейса `Repositories`, не замена локальному.

**Первичная заливка — переиспользовать существующий бэкап.** Формат
экспорта/импорта (JSON), который уже есть для ручного бэкапа, подходит
и как payload при первом входе: локальные данные заливаются наверх тем
же форматом, никакой отдельной миграции придумывать не нужно.

**Синхронизация v1 — простая, без live-конфликтов.** Полноценный
realtime-синк с разрешением конфликтов (если одновременно тыкать одну
рутину на двух устройствах) не нужен на старте. Для одного человека с
телефоном и ноутбуком это почти никогда не происходит по-настоящему
одновременно — «последняя запись побеждает» достаточно с запасом.
Подтягивание изменений — при открытии приложения, не постоянный
realtime-канал.

## Когда делать

Не сейчас. Это первый настоящий сервер в жизни приложения — то же
правило, что и в `docs/monetization.md`: не строить инфраструктуру
раньше, чем заработает и приживётся то, ради чего она нужна (сама
бесплатная механика, а тут — что вообще нужен второй человек на втором
устройстве). Инструменты для Supabase уже подключены в рабочей сессии,
так что технической подготовки не требуется — вопрос только в
очерёдности.
